## 核心概念（贯穿整个项目）

### 两种模型（不要混淆）

表格

| 模型 | 作用 | 运行时机 |
| --- | --- | --- |
| Embedding 模型（bge-small-zh-v1.5） | 文本转为向量，用于相似度检索 | 文档入库 ingest、本地知识库检索 retrieve |
| LLM 大模型（DeepSeek deepseek-v4-flash） | 生成答案、判断路由分支 | route 路由节点、generate 生成回答节点 |

### 真实运行 vs 单元测试（mock 替身）

1. 真实运行：模型 / API 真实调用
2. 单元测试：使用替身，不调用真实模型、不访问网络 / 数据库，测试速度快，专门测边界情况
   - 依赖注入：函数预留参数（`retriever=None` / `search_fn=None`），测试传入伪造函数
   - mock 打桩：`unittest.mock.patch` 替换网络请求，欺骗代码，返回写死假数据

> 
> 重点：mock 的假返回结构**必须和真实 API 完全一致**，否则测试通过，上线直接报错。

## Task2 定义 RAGState 状态（已完成）

文件：`src/adaptive_search_rag/state.py`

```
from typing import TypedDict
class RAGState(TypedDict):
    question: str        # 用户原始问题
    route: str           # 路由标记："retrieve" / "search"
    contexts: list[str]  # 参考上下文，本地文档/网页搜索结果
    answer: str          # 最终输出答案
```

要点：

1. 使用`TypedDict`，运行本质就是普通字典，**四个 key 必须全部存在**
2. 单向数据流：问题→上下文→答案，不是多轮对话，不用 MessagesState

## Task3 文档加载、文本分块、入库（已完成）

文件：`src/adaptive_search_rag/ingest.py` + `tests/test_ingest.py`

### 三个核心函数

1. `load_markdown(path: str) -> str`：utf-8 读取 md 全文
2. `split_text(text, chunk_size=500, chunk_overlap=50) -> list[str]`：文本切块
   - 步长 = chunk_size - chunk_overlap = 450 字符
3. `ingest_directory(dir_path, collection_name="adaptive_knowledge") -> int`：批量入库，返回 chunk 总数

### 关键知识点

1. Embedding：`SentenceTransformerEmbeddingFunction`，模型`BAAI/bge-small-zh-v1.5`，**local_files_only=True**离线加载，防止 HuggingFace 网络问题卡死
2. Chroma 持久化：`PersistentClient(path="./chroma_db")`，向量数据保存在本地磁盘
3. 集合操作：`upsert`（推荐，幂等，重复 id 直接覆盖），不要用 add（重复 id 抛异常）
4. chunk 唯一 id：`文件名#序号`，例如`rag-intro.md#0`

### 测试要点

- `tmp_path`自动创建临时文件，测试结束自动清理
- 这个测试会**真实加载 Embedding 模型**，等待约 20s 属于正常现象
- 项目语料：rag-intro.md、langgraph.md、agent-memory.md，一共切分出 15 个 chunk

## Task4 本地知识库检索节点 retrieve（已完成）

文件：`src/adaptive_search_rag/nodes/retrieve.py` + `tests/test_retrieve.py`

### build_retriever()

- 内部创建闭包函数 `retriever(question, top_k=3) -> list[str]`
- 配置参数必须和 ingest 入库代码保持一致：库路径、模型名、集合名
- 检索只读，只用`get_collection()`，不要 get_or_create_collection，避免 embedding 函数冲突报错
- 检索三步：
  1. 问题文本转向量
  2. chroma 集合执行 query 查询，返回 top_k 结果
  3. `docs = res["documents"][0]` 剥掉外层批次外壳，拿到一维 chunk 列表

### retrieve_node 节点函数

```
def retrieve_node(state, top_k: int = 3, retriever=None) -> dict:
    if retriever is None:
        retriever = build_retriever()
    question = state["question"]
    return {"contexts": retriever(question, top_k)}
```

依赖注入核心：

- 真实运行：不传 retriever，自动创建真实检索器，访问 Chroma
- 单元测试：传入伪造 retriever，不访问向量库，快速测试
- 只测试节点逻辑，Embedding / 向量库正确性在 ingest 阶段验证

### 测试用例

1. 正常检索：伪造 retriever 返回固定片段，断言 contexts 正确填充
2. 空库边界：伪造 retriever 返回空列表`[]`，验证不会崩溃

## Task6 联网搜索节点 search_node（已完成）

文件：`src/adaptive_search_rag/nodes/search.py` + `tests/test_search.py`

```
def search_node(state, top_k=3, search_fn=None) -> dict:
    if search_fn is None:
        search_fn = web_search
    question = state["question"]
    try:
        return {"contexts": search_fn(question, top_k)}
    except Exception as e:
        print(f"联网搜索出错：{e}")
        return {"contexts": []}
```

### 设计要点

1. 和 retrieve_node 输出格式完全一致，都返回`{"contexts": list[str]}`，下游 generate 不用区分上下文来源
2. 异常降级：网络 / API 报错捕获，返回空列表`[]`，**不中断 LangGraph 图执行**
3. 依赖注入：测试传入伪造 search_fn，模拟 API 崩溃场景

### 测试用例

1. 正常搜索：伪造函数返回网页片段，验证 contexts 结果
2. 失败降级：伪造函数主动抛出异常，断言 contexts 等于空列表，保证图不崩溃
